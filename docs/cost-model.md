# Cost model: size classes and slab carving

Why a GPU allocator cannot just use `g = 1.25` like jemalloc, what the size classes cost in
wasted bytes (and what the powers of two merged into the table since M5 buy), and where the model
stops being a model and starts being a guess.

Every number below is produced by the code in this repository or by arithmetic shown next to
it — nothing is estimated "by eye". The full sweep is
[`cost-model-sweep.md`](cost-model-sweep.md), generated by `tools/sweep_growth.cpp`; the
hand-computed values are pinned by `tests/test_size_classes.cpp`.

---

## 0. The result at a glance

Configuration v1.0: `s_min = 256 B`, `s_max = 2 MiB`, `g = 1.5`, `chunk_bytes = 2 MiB`.

| quantity | value | where it comes from |
|---|---:|---|
| size classes `k`, geometric progression | 23 | `SizeClassTable::count()`, §9.2 |
| internal waste, log-uniform, capacity-normalised | 17.790 % | closed form, §3 |
| internal waste, the same density integrated over the actual table | 18.028 % | Table E, §3.2 |
| internal waste, request-normalised | 21.640 % | `w/(1-w)`, §2.1 |
| expected tail waste, uniform resident weight | 3.461 % | `expected_tail_waste()`, §4 |
| total modelled waste | 21.251 % | §5, Table A row `g = 1.50` |
| retention bound (one chunk per class) | 46 MiB | 23 × 2 MiB, §5.3 |

Since M5 the library ships the **union** of that progression with the powers of two (§9):
`k = 34`, integrated internal waste 15.009 % (log-uniform) or **15.234 % on the committed trace**
against 23.915 % before, expected tail 2.342 %, retention bound 68 MiB. Every number in this
document that is labelled *geometric* describes the table above; §9 has the measured trade-off
and `include_power_of_two = false` restores the M4 table exactly.

The two honest caveats are stated where they belong: the closed form is a *design* number and
differs from the integrated one by 0.24 pp at `g = 1.5` (§3.2), and the total has **no interior
minimum** — `g = 1.5` is a policy choice on a frontier, not an optimum (§5).

## 1. Notation

| symbol | meaning |
|---|---|
| `s` | bytes requested by one allocation |
| `[s_min, s_max]` | range served by the pool; above `s_max` goes to the large path |
| `R = s_max / s_min` | 2^21 / 2^8 = 8192 |
| `f(s)` | request-size density |
| `g` | growth factor of the geometric progression, `g > 1` |
| `k` | number of classes |
| `c_i` | capacity of class `i` |
| `i(s)` | class a request of `s` bytes lands in |
| `w(s)` | internal waste of that request |
| `C` | `chunk_bytes`, the unit requested from the driver |
| `n_i` | blocks of class `i` in one chunk |
| `tail_i` | bytes of the chunk that no block of class `i` can use |
| `tau_i` | `tail_i / C` |
| `W_i` | resident weight of class `i` (bytes, blocks — only ratios matter) |

Geometric table, `i = 0 … k-1`:

```
c_i = s_min · g^i,      c_0 = s_min,      c_{k-1} >= s_max
k   = ceil( log_g R ) + 1
i(s)= min( ceil( log_g (s / s_min) ), k-1 )
w(s)= c_{i(s)} - s
```

`k` is the smallest count for which the last capacity covers `s_max`; the `+1` is there
because class 0 is a legitimate class, not an off-by-one.

**The shipped table is not exactly this.** Capacities are rounded up to a multiple of
`min_class_bytes` so that every block of a packed slab keeps the 256 B alignment the API
promises, and `k` is read from the rounded table (§6.1). Everything derived below from the
closed form — `E_int`, `k` in the un-rounded limit — is the *design* number; the generated
sweep file carries both.

Class 0 serves exactly one size, `s = s_min`: `s_min + 1` already needs `c_1`. In the
continuous model that class has zero probability mass, so it never affects an integral — it
exists so that the smallest requests pay nothing.

## 2. Expected internal waste, general case

For a request density `f`, the mean waste per request is

```
E[W_int] = sum_i integral_{c_{i-1}}^{c_i} (c_i - s) f(s) ds        (class 0: s = s_min only)
```

Numerically it is a mean over observed sizes — that is what
`SizeClassTable::expected_internal_waste(vector<double>)` computes. Two different
normalisations are in play and confusing them is how allocator benchmarks lie:

### 2.1 Capacity-normalised vs request-normalised

The model normalises by **assigned capacity**, `sum(c - s) / sum(c)`: "of the bytes the pool
hands out, what fraction is padding". The pool's `internal_fragmentation` metric is
request-normalised, `sum(c - s) / sum(s)`. They differ:

```
w_cap = sum(c-s)/sum(c)      w_req = sum(c-s)/sum(s) = w_cap / (1 - w_cap)
```

| `w_cap` | `w_req` |
|---:|---:|
| 10.372 % | 11.572 % |
| 17.790 % | 21.640 % |
| 27.865 % | 38.629 % |

Both are correct; the second is always larger. This document uses capacity-normalised
throughout and says so, because it is the one that has a closed form.

## 3. Log-uniform case: the closed form

Assume requests are uniform in log over `[s_min, s_max]`:

```
f(s) = 1 / (s · ln R),      R = s_max / s_min
```

On one class interval `[a, b]` with `b = g·a` the capacity is constant, so the conditional
mean waste is a ratio of two integrals:

```
E[W | s ∈ [a,b]] = integral_a^b (b-s) f(s) ds / integral_a^b f(s) ds
```

Step by step, with `ln(b/a) = ln g`:

1. numerator: `(1/ln R) · integral_a^b (b-s)/s ds = (1/ln R) · [ b·ln(b/a) − (b−a) ]`
2. denominator: `(1/ln R) · integral_a^b ds/s = (1/ln R) · ln(b/a) = ln g / ln R`
3. ratio: `( b·ln g − (b−a) ) / ln g = b − (b−a)/ln g`
4. divide by the capacity `b = g·a`:

```
E[W_int] / capacity = 1 − (g−1) / (g · ln g)
```

**Checks.** `g → 1`: with `eps = g−1`, `(g−1)/(g ln g) = 1 − eps/2 + O(eps²)`, so the waste
is `eps/2 → 0` — linear, while `k ≈ ln R / eps` explodes. That product, roughly constant, is
the whole trade-off of geometric size classes.

| `g` | `k` | `w_cap` = `1 − (g−1)/(g ln g)` |
|---:|---:|---:|
| 1.10 | 77 | 4.618 % |
| 1.25 | 37 | 10.372 % |
| 1.50 | 23 | 17.790 % |
| 2.00 | 14 | 27.865 % |

Hand check for `g = 1.5`: `0.5 / (1.5 · 0.405465) = 0.822101`, `1 − 0.822101 = 0.177899`.

`k` here is **not** `ceil(log_g R) + 1` any more: it is read from the rounded table (§6), and
rounding to the 256 B alignment floor moves it (24 un-rounded values would be 42, 24 and 14).

### 3.1 What the closed form is not

It is exact for a table whose classes tile `[s_min, s_max]` with full factor-`g` steps. The
real table is truncated at `s_max`, so the top class is only partly reachable, and classes do
not carry equal weight in a capacity-normalised mean.

### 3.2 Measured against the closed form

Integrating the same log-uniform density over the actual table (20 000 log-spaced samples,
`expected_internal_waste`, reproduced by Table E of `cost-model-sweep.md`):

| `g` | closed form | integrated over the table | difference |
|---:|---:|---:|---:|
| 1.10 | 4.618 % | 4.745 % | +0.128 pp |
| 1.25 | 10.372 % | 10.481 % | +0.109 pp |
| 1.50 | 17.790 % | 18.028 % | +0.239 pp |
| 2.00 | 27.865 % | 27.859 % | −0.006 pp |

Two effects, both worth naming:

* **Top class truncation.** At `g = 1.5` the last capacity is 3 107 072 B for a 2 097 152 B
  ceiling. Requests only arrive in the last `ln(2 097 152 / 2 071 296) / ln 1.5 = 3.06 %` of that
  class's log interval, which is exactly where `c − s` is largest — 32.5 % of capacity at
  `s = s_max` against 17.8 % for a complete class. The absolute waste is larger than before the
  alignment rounding, but so is the capacity it is divided by, which is why the difference
  barely moves.
* **Capacity weighting.** Every class holds the same probability mass under a log-uniform
  density, but the top class alone is 3 107 072 B of the 9 317 888 B total capacity — 33 % of
  the denominator — while holding 1 of the 23 equal-probability intervals (4 %).

At `g = 2` both effects vanish: `8192 = 2^13` exactly, so the last capacity **is** `s_max`.
The −0.006 pp residual is the Riemann error of the sample.

## 4. Slab carving

A per-block `cudaMalloc` would round a 64-byte tensor up to the driver's granularity
(~2 MiB, measured in M4). So chunks are carved:

```
n_i    = floor(C / c_i)              blocks per chunk
tail_i = C - n_i · c_i               bytes no allocation can ever use
tau_i  = tail_i / C
```

The rule that decides which chunk size a class gets is

```
chunk(c) = max(chunk_min, c)         so every slab holds at least one block
```

which gives three invariants, all checked for every class of every generated table in
`Slab::LayoutInvariantsHoldForEveryClassOfEveryTable`:

```
n >= 1,      n·c + tail == chunk,      tail < c
```

Worked case: `c = 700 000`, `C = 2 097 152`. `floor(2 097 152 / 700 000) = 2`, so
`n = 2`, `tail = 2 097 152 − 1 400 000 = 697 152` — 33.2 % of the chunk is stranded.

### 4.1 Why the tail is a sawtooth

`tail_i = C − n_i·c_i` with `n_i = floor(C/c_i)`. Inside one band `(C/(n+1), C/n]` the block
count `n` is fixed, so the tail falls linearly from almost `C/(n+1)` down to 0 at
`c = C/n`; one byte further, in the band with `n−1` blocks, it jumps back to about `C/n`.
The pattern repeats with every halving of `c`, i.e. it is approximately periodic in `log c`
with period `ln 2`.

Two consequences:

1. **There is no closed-form optimum in `g`.** `c_i = ceil(s_min·g^i)` is a step function of
   `g`: an infinitesimal change in `g` can move a class across a `tail = 0` point, so
   `E[W_tail](g)` is full of discontinuities and its minimum has to be searched numerically —
   which is why the size class table is an object in the code and not three constants.
2. **Classes above `C` are fine, classes just below `C` are not.** For `c >= C` the class gets
   its own chunk of exactly `c` and `tail = 0`; see §4.2 for the band underneath.

### 4.2 The `(C/2, C)` band: a wart of the carve rule

With `chunk = max(C, c)`, a class in `(C/2, C)` gets `n = 1` and `tail = C − c`, which can
approach `C/2`. From `cost-model-sweep.md`, Table C (default `g = 1.5`, `C = 2 MiB`):

| class | capacity | blocks | tail | `tau` |
|---:|---:|---:|---:|---:|
| 15 | 181 760 | 11 | 97 792 | 4.663 % |
| 16 | 272 640 | 7 | 188 672 | 8.997 % |
| 18 | 613 632 | 3 | 256 256 | 12.219 % |
| 19 | 920 576 | 2 | 256 000 | 12.207 % |
| 20 | 1 380 864 | 1 | 716 288 | **34.155 %** |
| 21 | 2 071 296 | 1 | 25 856 | 1.233 % |
| 22 | 3 107 072 | 1 | 0 | 0.000 % |

Class 20 alone strands 34 % of every chunk it touches. An earlier note in the design plan
claimed that a dedicated slab has `tail = 0`; that only holds for `c >= C`.

**The alternative, not adopted in v1.0.** Round the chunk up to a whole number of blocks:

```
chunk(c) = c · ceil(C / c)     =>  n = ceil(C/c),   tail = 0   identically
```

At the price of a bigger driver allocation:

| class | current chunk / blocks / tail | rounded chunk / blocks / tail | extra chunk |
|---:|---|---|---:|
| 700 000 | 2 097 152 / 2 / 697 152 | 2 100 000 / 3 / 0 | +0.136 % |
| 80 640 | 2 097 152 / 26 / 512 | 2 177 280 / 27 / 0 | +3.821 % |
| 613 632 | 2 097 152 / 3 / 256 256 | 2 454 528 / 4 / 0 | +17.041 % |
| 1 380 864 | 2 097 152 / 1 / 716 288 | 2 761 728 / 2 / 0 | +31.689 % |

Neither rule dominates: the first strands bytes inside a chunk, the second asks the driver for
more. Deciding needs the granularity experiment (M4): if `cudaMalloc` rounds 2 100 000 B up to
2 MiB-ish anyway, the rounded rule is free; if it rounds to the next power of two, it is not.
This is an open decision for M2, recorded here so it is not rediscovered later.

### 4.3 Expected tail waste over a class mix

```
E[W_tail] = sum_i (W_i / sum_j W_j) · tau_i
```

`expected_tail_waste()` implements exactly this. The weights are whatever the caller measured:
resident bytes per class for a real workload, or one unit per class to model requests spread
evenly over the table — the assumption behind the published sweep, and the reason §5 says so.

## 5. The sweep (91 growth factors, `1.10 … 2.00`, step `0.01`)

Full table: [`cost-model-sweep.md`](cost-model-sweep.md). Condensed:

| `g` | `k` | internal | tail | total | retention bound |
|---:|---:|---:|---:|---:|---:|
| 1.10 | 77 | 4.618 % | 5.558 % | **10.176 %** | 154 MiB |
| 1.20 | 44 | 8.586 % | 4.819 % | 13.406 % | 88 MiB |
| 1.25 | 37 | 10.372 % | 5.275 % | 15.647 % | 74 MiB |
| 1.30 | 32 | 12.042 % | 4.576 % | 16.619 % | 64 MiB |
| 1.40 | 26 | 15.085 % | 5.972 % | 21.057 % | 52 MiB |
| 1.50 | 23 | 17.790 % | 3.461 % | 21.251 % | 46 MiB |
| 1.60 | 19 | 20.213 % | 4.515 % | 24.728 % | 38 MiB |
| 1.70 | 18 | 22.401 % | 4.371 % | 26.771 % | 36 MiB |
| 1.80 | 16 | 24.387 % | 5.727 % | 30.114 % | 32 MiB |
| 1.90 | 15 | 26.201 % | 5.516 % | 31.717 % | 30 MiB |
| 2.00 | 14 | 27.865 % | 0.000 % | 27.865 % | 28 MiB |

(The `k` values are those of the rounded table: 77 classes at `g = 1.10`, not the 96 of the
closed form, because rounding to 256 B already groups several geometric steps into one class.)

### 5.1 The minimum is on the boundary, and that is the finding

`min(E[W_int] + E[W_tail]) = 10.176 %` at `g = 1.10`, the first swept value. The reason is
structural: `E[W_int]` **increases** monotonically with `g` (10.372 % at 1.25, 17.790 % at
1.5, 27.865 % at 2 — an earlier note in the design plan had the direction backwards), while
`E[W_tail]` only oscillates: its extremes over the 91 swept values are 0.000 % (`g = 2.00`)
and 6.797 % (`g = 1.63`), with no trend at all. A monotone term dominates a bounded
oscillation, so there is no interior optimum to find.

Two symmetrical readings, both worth writing down:

* The sawtooth is what would make an interior optimum possible; here it is too weak. At
  `g = 2.00` it collapses to 0 because every class is a power of two that divides 2 MiB.
* An objective that only counts bytes cannot express why more classes are worse. That cost is
  memory *retention*, and it is not in the formula.

### 5.2 What the objective is missing

A class retains at least one resident chunk the moment it is used, so with `k` classes the
worst-case resident memory is `k · chunk_min` (column above) — 154 MiB at `g = 1.10` against
28 MiB at `g = 2.00`. On an 8 GB card with several classes live, 154 MiB of retention bound
is a real constraint; 46 MiB is not. The exact number depends on the workload and is the job
of `resident_slack` (M3), not of this model.

### 5.3 Why `g = 1.5` then

Add the retention term and the objective finally has an interior minimum:

```
Cost(g) = E_int(g) · L  +  k(g) · C
```

`suggest_growth(live_bytes, chunk)` implements exactly this search over `g ∈ [1.05, 4.00]`,
with two documented approximations: `E_int` is the closed form (Table E says by how much it is
off), and `k_used = k`, the whole table, because the class mix of an unknown workload is
unknown — the worst case, which biases the answer towards fewer classes. Table D of
[`cost-model-sweep.md`](cost-model-sweep.md), generated by the same program:

| live set | optimal `g` | `k` | internal waste | retention | total |
|---:|---:|---:|---:|---:|---:|
| 64 MiB | 2.37 | 11 | 21.1 MiB | 22.0 MiB | 43.1 MiB |
| 256 MiB | 1.51 | 21 | 46.2 MiB | 42.0 MiB | 88.2 MiB |
| 1 GiB | 1.17 | 49 | 76.3 MiB | 98.0 MiB | 174.3 MiB |

So the answer is not one number, and the library does not pretend otherwise: it ships
`suggest_growth()` and defaults to `g = 1.5` for the case the model is worst at — a small live
set, which on 8 GB is the common one. For a 1 GiB live set `g = 1.5` costs 17.790 % of 1 GiB
(182.2 MiB) plus 46 MiB of retention, 228.2 MiB against the 174.3 MiB of `g = 1.17`: the
default is deliberately conservative, not optimal, and it is one field of `Pool::Config` to
change.

What the model *does* establish is that the choice is a policy, and it is why the table is
parameterised: once M4 replays a real trace, the same sweep runs on the measured histogram and
the answer can change without touching a single line of allocator logic. The published rule for
revisiting it is concrete: a measured waste that deviates more than 20 % from this prediction
buys a new `g` (or a class set derived from the histogram). §9 is that replay: the trace was
+32.6 % off, and the fix was the class set, not `g`.

## 6. Worked example, `g = 1.5` from start to finish

```
R      = 2^21 / 2^8 = 2^13 = 8192
ln R   = 9.010913,   ln g = 0.405465
log_g R = 9.010913 / 0.405465 = 22.2236   ->  ceil + 1 = 24 classes in the *un-rounded* table
c_22   = 1 915 348   (un-rounded: < s_max, so a 23rd class would be needed on top)
w_cap  = 1 - 0.5/(1.5 · 0.405465) = 1 - 0.822101 = 0.177899  ->  17.790 %  (21.640 % request-normalised)
```

Then the alignment rounding of §6.1 replaces the progression: `c_0 = 256`,
`c_{i+1} = round_up(ceil(c_i · 1.5), 256)` gives **23** classes, ending at
`c_22 = 3 107 072 B >= s_max`. `k` is what the table says, not what the logarithm says.

A 100 000-byte request lands in class 14 (`121 088`): 21 088 B of padding, 21.1 % of the
request. The class table (Table B of the sweep file) starts `{256, 512, 768, 1280, 2048, 3072,
4608, …}` and the growth column shows why: 384 B is not a multiple of 256, so the second class
is 512 and the local ratio is 2.0, not 1.5. That non-geometricity is precisely why `index_for`
is a binary search over the stored integers and not a logarithm (§6.1).

Modelled waste with uniform resident weight: 17.790 % + 3.461 % = **21.251 %**. Measured
against the same table with the density integrated instead of the closed form: 18.028 % +
3.461 % = 21.489 % — the 0.24 pp difference is the truncated top class (§3.2). Both are
published; the first is the design number, the second is what a log-uniform workload would
actually see.

### 6.1 The alignment rounding, and what it costs

A slab packs whole blocks back to back, so block `j` starts at `base + j·c`. The base is
256-aligned (a `cudaMalloc` guarantee the API promises to keep), so `c` must be a multiple of
256 or the second block breaks the promise. The un-rounded table fails immediately: class 1 is
384 B, class 5 is 1944 B.

Two ways to fix it, and they waste the same bytes:

| rule | capacity | block stride | reported as |
|---|---|---|---|
| round the capacity up (**shipped**) | 512 | 512 | internal waste |
| pad inside the chunk | 384 | 512 | tail waste |

The first is strictly better in practice: the extra 128 B can still be *used* by a 400-byte
request, whereas padding makes it unreachable. So decisions 11 of the design plan is what this
code does, and the price is visible in Table B: the table is no longer geometric at the bottom
(`256, 512, 768, 1280, 2048`), `k` drops from 24 to 23, and `E_int` for a request just above
`c_0` doubles.

The honest comparison is not "rounding is free": it is that the 256 B alignment guarantee
costs, at `g = 1.5`, one class out of 24 and 0.24 pp on the integrated internal waste. A finer
alignment (16 B) would keep the table geometric but would let the driver's own base alignment
leak into block offsets, which is exactly the bug this rounding exists to prevent.

## 7. Limits of the model

1. **Log-uniform is a placeholder density.** Real workloads are bimodal: few large, long-lived
   weights and many small, short-lived activations. The trace generator (M4) produces the
   histogram and `expected_internal_waste(vector<double>)` already accepts it.
2. **Capacity-normalised ≠ what the API reports.** `internal_fragmentation` divides by requested
   bytes; convert with `w_req = w_cap/(1 − w_cap)` (§2.1).
3. **`chunk_bytes = 2 MiB` is an assumption.** `cudaMalloc` granularity must be measured (M4);
   if it is larger than 2 MiB the default has to change, and every tail number here moves.
4. **Resident weights are assumed, not observed.** The published `E[W_tail]` weights each class
   equally; a real distribution can move it by a few percentage points in either direction.
5. **Slack is not modelled at all.** Blocks freed but not yet reusable (pending `cudaEvent`)
   are memory paid and unused; that is `resident_slack`, measured in M3, dependent on the load.
6. **Time is not in the model.** Every chunk costs a driver call, every free may cost a
   `cudaEventQuery`. If that cost exceeds ~5 % of `allocate`, reuse switches to epochs (M4
   experiment). A design that wins on bytes and loses on latency is not a win.
7. **Alignment: solved in M2, at a visible price.** Capacities are now rounded up to
   `min_class_bytes`, so every block of a packed slab is 256-aligned (§6.1). The cost is that
   the table is no longer geometric at the bottom (`256, 512, 768, 1280, …`) and `E_int` for a
   request just above `s_min` doubles. Pinned by
   `SizeClassTable.EveryCapacityIsAMultipleOfTheAlignmentFloor`.
8. **`index_for` is a binary search, not `ceil(log_g(s/s_min))`.** The closed form only matches
   an un-rounded table; with the alignment rounding it is off by one class over most of the
   range. `SizeClassTable.IndexForAgreesWithTheClosedFormOnUnroundedTables` states exactly where
   the identity still holds (a power-of-two table) instead of pretending it holds everywhere.

## 9. Why powers of two (M5)

### 9.1 The measurement that forced the change

M4 replayed `traces/inference_transformer.jsonl` and found **23.915 %** of internal waste
(capacity-normalised over the allocation histogram) against the **18.028 %** the log-uniform
model predicts: **+32.6 % relative**, outside the ±20 % criterion the plan sets. The cause was
not the model, it was the table: the weights of the trace are `hidden² · 4 B = 1 048 576 B` with
±5 % jitter, and the geometric table at `g = 1.5` has class 19 at **920 576 B** and class 20 at
**1 380 864 B**. Every weight sits between the two, so every weight paid between 20 % and 28 % of
its capacity in padding on a class that dominates the byte count.

Two candidate answers, and they are different questions:

* change `g` — makes *every* class narrower, including the ones that already fit;
* change the class *set* — keep the general-purpose progression, add the sizes the workload
  actually asks for.

M5 does the second, as a union, because it is what jemalloc does and because it is measurable on
the committed trace without touching `g`.

### 9.2 What the table is now

`SizeClassTable` builds the **union** of three sets, deduplicated and sorted
(`SizeClassTable::build`):

1. the rounded geometric progression of §6.1;
2. **all powers of two in `[s_min, s_max]`** — a tensor shape is a power of two, and so is most
   arithmetic derived from it; the switch is `Config::include_power_of_two`, default `true`, and
   `false` reproduces the M4 table exactly (`k = 23` at `g = 1.5`, pinned by
   `SizeClassTable.IncludePowerOfTwoFalseReproducesTheGeometricTable`);
3. **`Config::extra_sizes`**, for a caller that knows its own sizes, rounded up to
   `min_class_bytes` like every other capacity; out-of-range values throw `invalid_argument`
   instead of being clamped.

Every member stays a multiple of `min_class_bytes` and the table stays strictly increasing, so
`index_for`, `count()`, `blocks_per_chunk` and `tail_bytes` are unchanged: they read the array,
and there is still no closed form to get out of sync. `suggest_growth()` continues to model the
*geometric* progression (`include_power_of_two = false` internally): its `E_int` is the closed form
for that progression, and counting classes the closed form does not describe would add their
retention without their benefit. The union is a separate, measured knob.

### 9.3 Before / after, measured

`tools/measure_classes.cpp`, on `traces/inference_transformer.jsonl` (1538 allocs), M4 method:
histogram integral for the waste, full replay on `FakeBackend` for the resident set. The end-of-
replay snapshot is taken with every handle freed, so `resident` is what the pool still holds —
the retention this workload causes, as opposed to the worst-case bound.

| variant | `k` | internal waste | vs model (log-uniform 18.028 %) | expected tail | retention bound `k·C` | replay resident | replay tail | replay `tail_fragmentation` |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| geometric only (M4, `g = 1.5`) | 23 | **23.915 %** | +5.887 pp / **+32.6 %** | 0.962 % | 46 MiB | 82.0 MiB | 26.0 MiB | 31.668 % |
| powers of two (shipped) | 34 | **15.234 %** | −2.794 pp / −15.5 % | 0.543 % | 68 MiB | 68.0 MiB | 14.4 MiB | 21.111 % |
| geometric + `extra_sizes = {1 MiB}` | 24 | 15.815 % | −2.213 pp / −12.3 % | 0.584 % | 48 MiB | 66.0 MiB | 14.4 MiB | 21.750 % |
| powers of two + `extra_sizes = {1 MiB}` | 34 | 15.234 % | −2.794 pp / −15.5 % | 0.543 % | 68 MiB | 68.0 MiB | 14.4 MiB | 21.111 % |

Read the columns in pairs:

* **Internal waste: −8.68 pp, and back inside the criterion.** 23.915 % → 15.234 % is −36.3 %
  relative on the measured workload, and the deviation from the log-uniform prediction goes from
  +32.6 % to −15.5 %, i.e. **inside ±20 %**. The plan's rule ("more than 20 % off buys a new `g`
  or a class set") is satisfied by the class set; `g` stays 1.5.
* **The explicit 1 MiB class is most of the win on its own.** `extra_sizes = {1 MiB}` alone gives
  15.815 % with 24 classes: the weights are the problem, and one class fixes them. The powers of
  two then buy the remaining 0.58 pp on the power-of-two activation sizes for 10 more classes.
* **Tail goes down, not up.** A power of two in `[256 B, 2 MiB]` divides the 2 MiB chunk exactly,
  so the new classes have `tail = 0`; the classes the workload actually uses are packed better,
  and the replay's `tail_fragmentation` falls 31.668 % → 21.111 %. Expected tail over the trace's
  own class mix: 0.962 % → 0.543 %.
* **Retention bound grows, and it has to be said.** `k · C` goes 46 → 68 MiB (+22 MiB, +47.8 %).
  That is the "one chunk per class" term — not a ceiling on the workload's footprint, since a
  class can need several chunks (this trace's 21 weights each hold a chunk of their own, which is
  why the baseline resident set is 82 MiB and not 46). What matters is that the measured
  end-of-replay resident set goes **down**, 82.0 → 68.0 MiB, because the 11 extra classes pack the
  chunks the workload really uses: the tail alone drops 26.0 → 14.4 MiB. The bound is what a
  workload that touches every class once would pay — the price of the union, stated rather than
  hidden.
* **On the log-uniform placeholder the gain is smaller.** Table F of
  [`cost-model-sweep.md`](cost-model-sweep.md): integrated `E_int` at `g = 1.5` goes 18.028 % →
  15.009 % (−3.019 pp) for 11 extra classes. The placeholder cannot see the bimodality, so it
  under-sells the change; that is the same reason it mispredicted the trace in M4.

### 9.4 The trade-off, in one sentence

More classes are more retention and less rounding: the union costs **+22 MiB of worst-case
retention** and buys **−8.68 pp of internal waste and −11.6 MiB of measured tail on the trace**,
so it is a win wherever the live set is at least a few hundred MiB or the workload touches a
subset of the classes — and it is one flag away from the old table if that stops being true
(`include_power_of_two = false`).
